# 模拟实验后的框架修订

依据原站E03–E17及本地E18，以下结论属于inferred的自建设计建议。实验没有反向证明原站的内部实现。

| 原先推测 | 实验发现的反例/约束 | 修订方案 | 验证范围 |
|---|---|---|---|
| 异步任务失败后重试 | 平台已受理但响应丢失，盲重试可刊登两次 | 增加RECONCILE_REQUIRED；先查回执，幂等键覆盖重试与重启；查不到结果仍保留未知 | S03/S09；真实平台幂等和查询能力待确认 |
| 工作流读取商品资料 | 审核后编辑使任务输入过期 | 认领绑定草稿版本并保存输入快照；编辑使审核失效；按店铺/输入版本保证认领幂等 | S01/S02 |
| 同步按更新时间去重 | 同一事件重放与旧版本晚到是不同问题 | 收件箱事件幂等 + 对象版本检查；同键异值作为冲突单独处理 | S05/S09及50组乱序测试 |
| 同步成功推进水位 | 写入一半后推进游标会漏掉剩余订单 | 快照、幂等收件箱、发件箱和游标同一事务提交；游标以预期值比较交换 | S06；对象回滚模拟，非真实DB事务 |
| 发布错误统一重试 | 授权失效、限流与人工暂停恢复条件不同 | 区分WAITING_AUTH、RETRY_WAIT、PAUSED、FAILED与结果未知；保留恢复位置和下一可运行时间 | S01/S04 |
| 指标从每次同步累加 | 重复投递、取消和不同币种都会导致错误金额 | 按业务对象版本替换统计快照；记录投影位置及积压；取消撤销有效金额，币种分别汇总 | S07；退款/汇率等未实现 |
| 多平台统一接口 | 同一外部ID可能出现在多个租户和店铺，且能力不同 | 身份键包含租户、店铺、平台对象；连接器显式声明能力并在命令端验证 | S08；跨平台映射待实现 |

## 建议模块与提交边界

保留模块化单体起步方案，将连接器、商品与工作流、订单同步、统计投影分开建模。单进程可先获得清晰事务和审计边界；是否拆微服务仍由规模、可靠性需求与实测决定。

本地订单事务：校验租户和输入 → 事件去重/版本检查 → 更新订单快照 → 追加发件箱事件 → 提交游标。外部调用不应包进可回滚的本地事务。发布先持久化命令身份及输入，再调用平台；平台已受理而本地结果未知时转入对账。

统计消费发件箱事件，按对象版本更新投影并记录已应用位置；页面同时显示业务数据与统计积压。操作完成不等于统计已追平；HTTP200也不等于外部业务完成。

## 下一阶段实现门槛

1. 选择真实数据库，验证订单/收件箱/发件箱/游标的事务提交及故障恢复，测试多个同步器竞争同一游标。
2. 引入持久化队列/任务租约，测试执行器崩溃、重复取任务与外部超时；不能把当前JSON恢复当作生产耐久性。
3. 在平台沙箱确认幂等键、结果查询、版本/更新时间和授权生命周期；按能力调整适配器。
4. 以只读或隔离数据验证真实分页、回调、来源映射和指标口径。供应商选择与商业转化仍不在本轮范围。
