# REA 方法在本项目中的应用

本轮采用 REA 的证据与调查原则，执行工具仍是 Tabbit CLI；没有安装、注册或运行 REA MCP/CLI，也没有生成 REA 原生 Evidence bundle。本仓库的 E编号是自己的研究索引，不应传给 REA 当作原生 Evidence ID。

## 本轮调查问题与执行

问题：ERP 哪些页面读取同一后端？选品、店铺授权、工作流、平台商品、订单、统计是否存在可观察的接口分界？这些证据对第三方接入设计能说明什么？

1. 以首轮页面证据建立假设，明确哪些只能由后端证据解决。
2. 接管已授权 ERP 标签页，在页面级 CDP 中监听请求与响应事件，再导航到已观察过的页面。没有重放接口或构造业务请求。
3. 仅保留方法、同源路径、HTTP状态和页面分组；去掉查询串及片段，数字/长十六进制路径段归一化。不读取请求头、Cookie、存储、请求体或响应体。
4. 按 `(页面分组, 路径)` 汇总方法和状态集合，筛选核心业务路径；从全部网络事件中排除通知、商业权益及资源加载等无关记录。原始请求次数和顺序不属于此汇总产物。
5. 将事实写入 evidence.json 与 api-observations.json；把架构假设、替代解释及验证条件写入 hypotheses.json；映射到 traceability.json。
6. 停止 CDP 观察、结束任务并保留标签页；执行本地检查后提交推送。

## 覆盖与反证纪律

采样只覆盖7个页面阶段，单批最多保留160条请求记录，最终导出35条页面/路径记录；被选择批次的容量丢弃计数为0。这不表示完整覆盖所有接口、第三方域名、后台任务或未来请求。

第一阶段的方法与响应事件按页面/路径归并；后续阶段使用临时 requestId 配对响应，并在导出前丢弃该ID。网络空闲等待失败不能被解释为页面失败；上架任务页仍取得200响应。订单页没有匹配的语义表头，改为检查实际页面状态和已捕获元数据，没有重试任何业务写操作。

200只代表HTTP响应已观察，不证明业务成功、授权仍有效、平台数据最新或正文结构符合预期。POST也不自动表示业务写入。未捕获到第三方请求不能证明没有第三方接入：本轮主动只保留ERP同源请求，后端到平台的流量不可见。

页面自然发起了 `/erp/track/collect` 的POST，以及 `/sys/userPreference/save` 的PUT。没有主动点击保存或改变设置；没有读取正文，所以不能判定偏好具体是否变化。这说明页面浏览也可能存在应用自行发起的副作用，不应声称完全没有写请求。
