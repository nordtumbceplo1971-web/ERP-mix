# 由业务反推系统框架

这是学习项目的建议架构，非对原站源码、数据库或部署方式的鉴定。依据见 research/traceability.json。

第二轮已用同源请求元数据补充授权、选品、任务、订单、统计和在线商品接口的分界（E11–E17）。详见 [外部API分析](api-integration-analysis.md)。第三方供应商、后端连接器、Webhook、增量同步及部署方式仍未证实；不要将路径名直接当作微服务或数据库表结构。

## 建议的对象关系

SourceProduct 保存来源引用；ProductDraft 聚合审核资料与 SKU；Claim 将草稿和目标店铺/平台配置关联；WorkflowRun 包含 TaskNodeRun 和发布结果；PlatformListing 保存平台商品引用与快照；CreativeTask 关联素材产物；Order 包含 OrderLine，Shipment 关联运单与履约状态；MetricSnapshot 保存统计窗口及口径。

这些实体名是 inferred。是否一份草稿可认领多店、是否多运单/拆包，需验证后确定基数；不直接推断外键或数据库表名。

## 状态维度

- 商品资料：认领/上架分组、核对状态、AI核价状态、自动刊登状态分别保存（E03）。
- 上架任务：排队中、运行中、待发布、发布中、已完成、已暂停、异常（E04）。
- 平台商品：在售、售罄、审核、未上架、禁售、删除；优化任务另有独立状态（E05）。
- 订单：待处理、待打单、待揽收、已交运、已搁置、已取消（E06）。

上述为 observed 的状态标签；相互迁移的条件、顺序、可逆性均为待验证。尤其不能用单个 status 字段混合商品平台状态和内部任务状态。

## 实现方向

首期建议采用模块化单体，加独立异步任务执行器；平台连接器隔离各平台数据差异。同步/生成/发布任务适合队列执行，前端读取任务进度。关系型存储保存业务关联，对象存储保存媒体，统计投影支撑工作台。这些都是 inferred 的工程选择，不是原站技术栈结论。

发布、订单同步和运单操作建议建立幂等键、外部回执、可审计事件与补偿流程。状态变更需记录操作者、来源、时间、前后状态、任务/业务对象ID和失败原因。权限按企业与店铺边界校验，浏览器会话与仓库证据分开保管。

优先实现顺序：领域契约与模拟适配器 → 单商品流程 → 异步任务监控及恢复 → 平台适配 → 订单履约 → 指标投影。收费/推广模块保持独立，只暴露必要的权益检查接口。
